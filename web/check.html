Aegis / check an address

Check an address before you pay it.

This is the deterministic half of the Aegis engine, running in your browser against Arc testnet's public RPC. No backend, no key, no account, and nothing leaves this page but the address itself, in read-only calls to a public gateway. It also asks the deployed AegisGuard what it would do, which is the answer that actually binds.

What this page is, and what it is not

The point of putting it here is that you do not have to take the README's word for anything. Paste an address and watch the same code run.

  • The LLM second pass does not run here. It goes through the claude -p CLI on a local machine, which a browser cannot do. That is not a hole improvised for this page: the engine already has that branch, because the CLI can be missing or time out, and when it is unavailable the engine falls back to the deterministic verdict. So what you see here is the real engine in its LLM-unavailable mode, not a simplified copy of it.
  • What that costs you is precision, in one direction. A HIGH bytecode score reads as BLOCK here. With the LLM reachable it stays BLOCK if the model agrees, and becomes ASK_HUMAN if the model thinks the alarm is a false one. The browser never auto-downgrades, so this page is the more paranoid of the two.
  • The opcode scan is a linear walk. It tells you a dangerous opcode is present, not that it is reachable. It over-flags on purpose, in the direction where a mistake is cheap.
  • The verdict on this page binds nothing. It is an opinion computed in your browser. The verdict that binds is AegisGuard.assess, which runs on Arc inside the transfer, and which the panel above reads live so you can see both.
  • Reputation is a mock lane and says so. The lists that are real are the guard's own denylisted and allowedContract mappings on-chain, which show up in the assess result rather than here.
  • This page believes whatever the gateway answers. It scans the code an Arc gateway hands back, so a gateway that lied would produce a confident, clean verdict and nothing here could tell. That is true of any off-chain analyzer, including the one in the repo, and it is the clearest reason the on-chain layer exists: guardedPay reads the recipient's code from chain state inside the transaction, with no RPC in the loop to lie to it.
  • The lane code on this page is the code in the repo. test/web-check.test.mjs lifts this file's script block out, runs it and src/lanes/bytecode.js over the same bytecodes, and fails if the two ever disagree. Copy-paste that drifts is worse than no copy at all, so it is pinned.
